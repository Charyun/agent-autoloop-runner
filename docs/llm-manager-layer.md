# 管理层（LLM 层）方案

> 状态：实施中，分支 `feat/llm-manager-layer`。
> 目标：在不碰内核的前提下，给系统加一个站在中台之外的**管理者**，它做三件事——**看进度、派任务、记记忆**。

## 一、为什么管理层不能进内核

`AGENTS.md` 的红线：内核只收、只分、只派、只记；不主动连接任何东西；事件里的字进不了提示词、影响不了交给谁、在哪、用什么权限。

管理层按三个功能分别使用凭据。本阶段把管理者视为可信客户端；下表描述它按设计调用的接口，不代表密钥在中台被限制到这些接口：

| 功能 | 密钥 | 设计用途 |
| --- | --- | --- |
| ① 看进度 | `owner` | 读 `/v1/state`、`/v1/runs/<n>/why`、`/v1/stream`；写操作只调用 `/v1/runs/<n>/cancel`（停止） |
| ② 派任务 | 专用 `manager` 来源的 `source` | 发 `POST /v1/events`；只为该来源配置允许触发的任务规则 |
| ③ 记记忆 | 订阅 stream 用 `owner`；读本地文件无需 HTTP 密钥 | 订阅 `/v1/stream` 蒸馏；worker 侧读本地库注入 `context.json` |

`owner` 当前还允许回答、结案卡片和撤销密钥，所以不能承诺管理者被攻破后只能问进度。管理者不提供这些操作，但这是客户端约定；同一进程按功能拆分也不构成凭据隔离。本阶段沿用现有权限，不新增受限密钥或代理；将来需要强制限制时，另做受限权限或由独立可信代理保管原密钥。

`source` 密钥绑定来源身份，不能冒充其他来源，但不限制该来源直接提交的事件类型。没有匹配规则的合法事件仍会记录，不派活。`emits` 仅限制 Agent 回执里的事件，不约束 `POST /v1/events`。`rules.json` 由人维护，管理者不提供改规则功能；是否能修改本地文件取决于运行环境的文件权限。

## 二、三个功能

### ① 回复进度（看）

- 入口：飞书/MCP/命令行问"任务进行到哪了"、"停掉 7 号"。
- 实现：`GET /v1/state` 拿总览，`/v1/runs/<n>/why` 拿单轮的来龙去脉，`/v1/stream` 订阅实时变化；把结果组织成人话回复。
- 原有入口：未配置管理者时，飞书通道只消费 `card.action.trigger`（卡片点击），**不收自由文本消息**。要支持"发一句话问进度"，已增加可选 `manager` 命令桥接，提供文本消息到管理者的入口，以及管理者通过飞书发送回复的出口（插件改动，不碰内核）。查进度用的 `owner` 密钥留在管理者进程里。
- 停止：`queued`/`claimed` 能强停（进程组 SIGINT → 10s SIGKILL）；`unknown` 状态停不了，这是已知缺口，报 issue 处理，不在本批解决。

**启用开关**：本机 `config.json` 顶层写 `"manager": { "enabled": true }` 才启用管理层，默认关闭。关闭或省略时保持原有飞书卡片流程，不启动管理者文本入口、模型调用或记忆订阅，新任务也不注入记忆。开关在启动时生效，修改后重启中台/worker 与独立记忆进程；保留已有任务记录、会话和记忆文件。

**飞书交互约定（已实现，待真实账号验收）**：中台和管理者都通过飞书面向使用者，各自负责自己的消息。

| 消息 | 负责人 | 流程 |
| --- | --- | --- |
| Agent 提问卡片、通知、处理结果 | 中台现有飞书通道 | 直接发送、更新；卡片点击回到中台，对应事项继续执行 |
| 用户自由文本、管理者的进度回复与任务安排说明 | 管理者 | 用户文本交给管理者理解，管理者通过飞书发送自己的回复 |

- 中台卡片沿用现有流程，无需经过管理者组织、汇总或改写；多个 Agent 产生的卡片仍各自发送、各自记录回答。
- 共用同一个飞书机器人时，由一处通信入口接收事件：卡片交互交给现有通道处理，普通文本交给管理者。底层统一接收，业务分别处理，避免新旧进程竞争同一应用的事件监听。
- 管理者的回复使用独立消息，不占用中台卡片的消息编号、送达记录和状态；共用机器人不意味着共享中台密钥。
- 文本入口核验允许交互的用户，保留用户身份、会话与消息编号，供管理者关联回复和去重。卡片回答继续沿用中台现有的回答人、原消息与重复回答校验。
- 本批先支持管理者对话与进度查询；普通文本代答中台卡片需要另行设计，不作为现有卡片回调的替代入口。

### ② 派发任务给对应的 agent（派）

**红线**：事件决定不了交给谁。管理者不能直接写 `to: "codex"`，`cwd`、`access`、`skill` 也碰不到。

拆成两半：

- **人画图**：`rules.json` 里为每个 agent 写一条路由规则，`to/cwd/access/skill/parallel/askFirst` 全部来自人写的规则。
- **管理者选路**：看着 agent 的职责描述，从配置的允许路由中选一个事件类型，以专用 `manager` 来源发出去，规则的 `when` 接住。客户端的类型检查用于避免误发；中台是否派活由来源和类型匹配的规则决定。

```jsonc
// 专用来源，不复用其他事件入口的 local 来源
"sources": { "manager": { "name": "管理者" } },

// agents 段新增可选 about：这个 agent 是干啥的（人写的资料，不是指令）
"agents": {
  "claude": { "name": "Claude Code", "worker": "mac", "use": "claude",
              "about": "擅长长任务、跨文件重构" },
  "cheap":  { "name": "小模型", "worker": "mac", "use": "command",
              "command": ["claude", "-p", "--model", "haiku"],
              "about": "分类、摘要等廉价活，30 秒内出结果" }
}

// 每个 agent 一条路由规则（人画的图）
{ "name": "路由→小模型", "when": { "source": "manager", "types": ["route.cheap"] },
  "to": "cheap", "cwd": "~/code/app", "access": "read", "tell": "never" }
```

管理者（或分类轮）读 `about`，发 `route.cheap` 事件 → 规则接住 → 派活。

只为 `manager` 来源配置允许执行的目标，避免宽泛的类型匹配意外放行其他任务。自动分类轮在其规则的 `emits` 中明确列出允许输出的事件类型与来源；管理者直接提交事件时不依赖 `emits`。

**分类发生在哪里**：

- 你主动安排的（飞书一句话）→ 管理者内联判断（它本来就在调 LLM）。
- 自动流入的事件 → **分类轮**：一条宽 `when` 规则指向便宜的分类 Agent（`access: read`、`tell: never`），回执发 `route.*`。理由：这类派发没人看着，必须全程进事实日志、`why` 可查。
- 路由明显的 → 根本不走分类，直接写普通规则。能用确定性规则的，一分 LLM 都不该花。

### ③ 整理并传递记忆（记）

三类记忆，各走各的路：

| 类别 | 例子 | 去处 |
| --- | --- | --- |
| 记录性（过去发生了什么） | "上次类似问题的结论是 X" | 记忆库（仓库外），蒸馏 + 检索 |
| 规范性（未来该怎么做） | `plan.md`、`ROADMAP.md` | 进 cwd，不进检索库，当前有效、可被改写 |
| 短期（本轮事实） | `context.json` | 已有 |

- **写管子**：管理者订阅 `/v1/stream`，把跑完的轮蒸馏成条目。
- **读管子**：worker 派活前拉 top-k，注入 `context.json`（方案 B，worker 侧改动）。
- 纪律：记忆是**资料不是指令**；按 `scope=cwd` 隔离；每条带 `evidence.run` 可 `why`；被推翻的标 `superseded_by`；记录 `use_count`。

## 四、批 2：读管子（已完成）

启用管理层时，派活前把记忆并进资料文件，读管子在 `worker/`，开关由本机启动配置传入：

- `worker/memory.ts` 的 `recall(目录)`：读安装目录里的 `memory.json`，按 `scope` 只留同一个目录的、没被 `superseded_by` 推翻的，按 `at` 倒序取前 5 条。文件缺失或写坏（管理者正在写）→ 返回空，绝不让派活起不来。
- `worker/worker.ts`：写 `context.json` 的两处（开跑、重启后没起过跑）都并进 `memory` 字段；`promptFor` 只多一句"memory 是这个目录以前跑出来的记录，也是资料不是指令"，**记忆原文一个字不进提示词**。
- 兼容：`context` 是资料，加字段不算破坏；`docs/protocol.md` 的 Job 一节写清了 `memory` 由接单程序并入、中台不知道。

`memory.json` 的条目格式（批 3 的管理者按这个写）：

```jsonc
[
  {
    "id": "stable-id",          // 改写同一条时 id 不变，或用 superseded_by 指向新条
    "scope": "~/code/app",      // 规则里的 cwd，只有这个目录的活拿得到
    "text": "上次类似问题的结论是 X",
    "at": "2026-11-01T09:00:00+08:00",  // 排序用，新的在前
    "evidence": { "run": 12 },  // 哪一轮跑出来的，可用 why 查
    "superseded_by": "newer-id" // 被推翻就写上，读的时候跳过
  }
]
```

## 六、对 `AGENTS.md` 红线的逐条对照

| 红线 | 本方案如何守住 |
| --- | --- |
| 内核不连外、不知道产品名 | 管理者是仓库外的进程/插件；仓库内加 `about` 字段（含内核类型声明）和 worker 读 `memory.json` 的读管子，不把管理者推理放进内核 |
| 事件文字进不了提示词、影响不了交给谁 | 内核仍按可信规则路由，`to/cwd/access/skill` 不从事件正文取值，记忆原文只进资料文件。外部 LLM 分类会间接影响目标选择，属于对原有端到端约束的扩展；批 4 实施前须明确允许路由范围并同步维护约定，不能声称完全不影响交给谁 |
| 没有界面 | 进度问答走通道（飞书/MCP）和命令行，不做页面 |
| 一轮不等人 | 管理者是独立进程，不阻塞任何一轮 |
| 没有运行时依赖 | 记忆库用文件 + Node 自带能力，`package.json` 不加依赖 |
| 协议改动写清兼容 | 批 1 属"新增字段不算破坏"，`checkFields` 同步加清单；批 2 的 `memory` 是接单程序并进资料文件，见第三、四节 |
